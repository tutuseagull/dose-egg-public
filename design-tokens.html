DoseEgg Design Tokens

A first token set to react to, not a finished system. ~30 names total — deliberately small. Every name here should survive a change of palette; if renaming a value forces renaming a token, the token was named wrong.

Palette decided 2026-08-05 — "Oat + petrol." Chosen over ten alternatives across four exploration sheets. The organising idea is temperature tension: a warm-undertoned ground against a cool-undertoned ink. Every palette where accent and neutrals shared a temperature read as flat — harmony turned out to be the opposite of interest.

1. Oat neutrals. Warm, but pulled back from cream — greyer, less yellow. Keeps the paper feel without the familiar AI-product association.

2. One low-chroma petrol accent. Deep blue-teal, cool against the warm ground. Contrast carries emphasis instead of hue — which means colour can never accidentally rate anything. The palette enforcing the no-verdict rule structurally.

3. Serif headlines, sans body — still provisional. Type options come next, including a sans-chrome / serif-for-the-user's-words inversion. Unlike the palette, this one hasn't been properly explored yet.

Component and layout treatments in these examples are placeholders — the UI language is not decided, only the tokens.

Text size & system scaling

Every size in the scale is rem, which means all of it moves from a single root value. That is the whole mechanism — never build a second hardcoded set of sizes. Two sets double the maintenance and drift apart within a month.

html { font-size: 100%; }        /* one knob */
html[data-text-scale="large"]  { font-size: 112.5%; }   /* 17px → 19px */
html[data-text-scale="larger"] { font-size: 125%;   }   /* 17px → 21px */

Who owns text size — the OS or the app? Both, and in a WebView it is messier than native. This is a real accessibility cost of the Capacitor decision, worth knowing now rather than discovering later:

PlatformSituation
iOS nativeDynamic Type. Nearly free.
iOS WKWebViewfont: -apple-system-body in CSS does follow Dynamic Type — it's been in WebKit for years. But WKWebView has no adjustsFontForContentSizeCategory, so changing the setting mid-session needs native code listening for the content-size-change notification. Open Capacitor issue (#7770).
Android WebViewApplies the system font scale to textZoom by default; can be read explicitly via Settings.System.FONT_SCALE + WebSettings.setTextZoom().

So: do both. Follow the system scale where it works, and ship an in-app text-size control. The second isn't redundancy — someone may want large text in a medication journal without enlarging their entire phone, and for this audience reading ability genuinely varies between an ON and an OFF period within the same day. A setting they can change in thirty seconds is a real feature, not a fallback.

And design to survive it: WCAG 1.4.4 requires 200% resize without loss. No fixed-height text containers, no truncation, no single-line assumptions.

The rule that matters most

A day with no data must never be drawn as a value. Here is why, with the same week rendered both ways — Wednesday was not logged:

✗ Missing drawn as zero

Wednesday now reads as the best day of the week — zero symptoms. It's a lie, and it's the kind that ends up in front of a neurologist.

✓ Missing drawn as a gap

The gap is visible and labelled. The reader sees absence of data, not absence of symptoms. Same dashed-hollow language as the unknown entry state.

Series colour — same lesson as the entry marks

Maximum four series. Always paired with direct labelling or shape, never a colour-only legend — for the same colour-vision reason established above. And no severity gradients: a sequential colour scale is a ranking, which is a verdict. [C-08]

Deliberately absent

What a token set refuses to name matters as much as what it names. None of these exist, and adding one should require a decision, not a convenience:

  • No success / error / warning for health data. --feedback-error exists for app failures only — bad input, network down. There is no token for a body being wrong.
  • No severity scale. No severity-1…5, no red-amber-green. A scale invites ranking, and ranking is a verdict. [C-08]
  • No adherence or completion colour. There is nothing to score. [C-08]
  • No hover-only states. Touch has no hover. Press states only.
  • No elevation/shadow scale yet. Borders and surface tone carry separation. Shadows can come later if something genuinely needs to float — and each one should be argued for.

One usage rule: --text-muted on --surface-sunken is 4.24:1 — below the 4.5 threshold. Muted text is not permitted on sunken surfaces at body size. Use --text-secondary there.

Fixed — non-text contrast (1.4.11)

The original --border-strong (paper-300) was 1.36:1 and the unknown-state dot (paper-400) was 1.86:1. Both fail the 3:1 requirement for component boundaries — which meant the epistemic indicators were invisible to a low-vision user. Given that this distinction is what stops an assumed dose reading as taken, that was the most serious finding in the audit.

Fixed by splitting borders into --border-subtle (decorative only) and --border-interactive at paper-500 (3.2:1), and moving both epistemic outlines onto it.

Fixed — focus indicator (2.4.7)

No focus tokens existed. Added --focus-ring / -width / -offset. Not optional here: tremor makes touch unreliable, so keyboard and switch-control paths matter more for this audience than for most.

Unresolved by colour — the entry marks

Simulated under all three types of colour-vision deficiency, the five marks collapse:

PairProtanopiaDeuteranopiaTritanopia
symptom / note1.011.091.02
activity / note1.041.051.00
symptom / activity1.051.141.02

1.00:1 means identical. This is not a fixable palette problem — it's a direct consequence of the design goal. Equal lightness is what makes the marks unranked, and equal lightness is also what makes them indistinguishable. Pulling them apart in lightness would reintroduce a visual hierarchy among entry types, which is the thing we were avoiding.

So colour is demoted to the secondary channel. Icon or shape always carries the entry type; colour reinforces it for people who can see it. This is better product design anyway — an icon says "meal" directly, whereas a colour requires learning a legend.

Touch targets — pass

--touch-min at 48px clears WCAG 2.5.5 (44px) with margin. Keep the margin; 44 is a floor for the general population, not for tremor.

Icons — decided 2026-08-05: Phosphor

Icons carry entry type rather than decorating it, because colour failed the colour-vision test. Chosen over Lucide on two grounds: Phosphor ships a native fill weight, which gives the solid/hollow pair the epistemic states need without building a mechanism to maintain; and its bold weight is a real accessibility lever, since thin strokes fail first for low vision. Comparison and the size tests live in icon-candidates.html.
